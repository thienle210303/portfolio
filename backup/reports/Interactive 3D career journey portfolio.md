# Cut the font, then build the planet

Build Playground Earth exactly as committed — and pay for it with one line of font configuration. The research says the globe is the right instinct and the wrong worry: the Canvas 2D orthographic projector already in hand costs **1.8 ms per frame at 1440px with zero animation frames at rest**, which is roughly 11% of a 60 Hz budget, and the Canvas→WebGL crossover is nowhere near a scene of this complexity. The real constraint is somewhere nobody was looking. **Next 16's shared runtime measures 127.6 KB gzipped on this exact build**, which against a ~190 KB total-JS budget leaves **62.4 KB for every line of application code on every route** — and two chunks on `/` today, the Companion at 25.8 KB and one unidentified app chunk at 38.7 KB, already total 64.5 KB between them. Meanwhile the font payload is carrying roughly **100 KB of pure optical sizing**: instancing the real built files shows that **pinning Newsreader's `opsz` axis takes the whole font payload from 331.4 KB to 137.1 KB — a 58.6% cut — while keeping a genuine italic and a 400–700 weight range**. That settles the project's long-running italic argument in the opposite direction from the one everyone expected, because a real italic, instanced, costs **40.9 KB**, not 143.6. That is the shape of the whole answer: the fancy, 3D-feeling, luxury thing Thien wants is affordable, but only if it is bought with bytes reclaimed from typography and hydration rather than borrowed from a library. The evidence also carries three warnings worth more than any technique in it — roughly **85% of readers never touch an interactive graphic**, the 2026 "blueprint" aesthetic is now a documented trend rather than a differentiator, and there is **no published evidence that creative portfolios produce hires** — and each of those is a design constraint that makes the work better, not a reason to build less.

---

## The constraints, stated once

Next.js 16 App Router, React 19, TypeScript strict, Tailwind v4 configured via `@theme` in CSS with no `tailwind.config.js`, pnpm only, no database, no CMS, no component library, deployed on Vercel Hobby. Roughly **190 KB gzipped of JavaScript for the whole site**. All content lives in static TypeScript (`src/content/portfolio.ts`, `src/content/ai-experiments.ts`) and components read from it without restating a fact. The Blueprint system keeps two strictly independent axes — theme (`day`|`night`, the visitor's) and tone (`base`|`deep`|`contrast`, the author's per-section) — with components styling against semantic aliases only, blue reserved for annotation, links, measured values and one primary control per screen, and a margin rail carrying facts computed from the content layer. Targets are WCAG 2.2 AA and Lighthouse 90+/95+/95+/95+. three.js (~133 KB gz), `@react-three/fiber`+drei (~254 KB), `globe.gl` (~509 KB) and `cobe` are already measured and rejected. The proven foundation is the existing no-dependency Canvas 2D orthographic globe. Every recommendation below lives inside that.

## Two thirds of the JavaScript is framework, and optical sizing costs 100 KB

The single most useful thing in this research is an arithmetic that has never been written down in this project. Fetched with gzip from a running `next start` against the `claude/round-16-demolition` build, the chunks Next loads on *every* route total **130,670 bytes = 127.6 KB gzipped**: React plus React DOM at 71,614 B, the App Router client runtime at 43,848 B, a `next/dist/compiled/process` polyfill at 7,359 B, the Turbopack runtime at 4,284 B, and one further 3,565 B chunk *(measured in-repo, 2026-09-29, via `curl -H "Accept-Encoding: gzip"` against `next start -p 3100`)*. An independent practitioner re-baseline lands within 1.5 KB of that, reporting the Next 16 shared runtime at **129 kB gzipped against 94 kB on Next 14** ([jgt7405/analytics-frontend PR #10](https://github.com/jgt7405/analytics-frontend/pull/10)). So the floor is real, it is not this project's fault, and it is not going away.

Subtract it and **62.4 KB remains for all application code**. That number should be pinned above the desk, because it silently prices every proposal anyone will ever make. three.js at ~133 KB gz is **more than twice the entire application allowance**; `globe.gl` at ~509 KB is eight times it. The smallest credible WebGL helper measured, `picogl` 0.17.9 at **15,195 B gzipped**, is 24% of the allowance before a single line of scene code, and `ogl` at **34,177 B** is 55% ([Bundlephobia, 28 Sep 2026](https://bundlephobia.com/api/size?package=ogl)). The scroll libraries are no better: GSAP core plus ScrollTrigger is reported at **~46 KB gzipped**, roughly three quarters of the allowance, and even Lenis at a reported ~3.6 KB is not free ([Born Digital comparison](https://www.borndigital.be/blog/our-smooth-scrolling-libraries)). The honest conclusion the notes reach, and I agree with, is that **no animation or 3D library is affordable without deleting something that already exists** — and there is nothing on this site worth deleting to buy one.

**But the JavaScript is not where the money is.** The site preloads five WOFF2 files totalling 339,320 B = **331.4 KB**: Newsreader 16pt Italic at 147,060 B (143.6 KB), Newsreader 16pt Regular at 131,848 B (128.8 KB), IBM Plex Sans Regular at 40,240 B (39.3 KB), and IBM Plex Mono SemiBold and Regular at 10,120 B and 10,052 B (9.9 and 9.8 KB). **Newsreader alone is 82.2% of all font bytes.** Both Newsreader faces carry 262 glyphs across 224 codepoints and a *two-dimensional* variation space — `wght 200–800` crossed with `opsz 6–72`. The two Plex faces are already near-optimal; leave them alone.

Instancing and re-subsetting the actual built files rather than asking the Google Fonts API for variants produces the decisive table. Each row re-subsets to latin and re-packs to WOFF2 after the instancing step, so every figure is a real transfer size for the italic face:

| Newsreader italic, latin | Size | Δ |
|---|---|---|
| Baseline, as shipped today | **143.6 KB** | — |
| Repack only, no changes | 141.2 KB | −1.5% |
| `wght=400:700`, `opsz` kept | 101.0 KB | −29.6% |
| `opsz 16–48` + `wght=400:700` | 90.3 KB | −37.1% |
| **`opsz` pinned + `wght=400:700`** | **40.9 KB** | **−71.5%** |
| `opsz` pinned + `wght=400:600` | 39.5 KB | −72.5% |
| `opsz` pinned + `wght=400:700`, used glyphs only | 24.6 KB | −82.9% |
| `opsz` pinned + `wght=400` static | 21.4 KB | −85.1% |

*(Measured in-repo, 2026-09-29, with fontTools 4.66.0 against `.next/static/media/*.woff2`. These supersede an earlier pass that priced variants through the Google Fonts CSS2 API; the two agree on direction and disagree on magnitude, and these are the ones measured on this build.)*

**The load-bearing insight sits in the gap between rows four and five: narrowing `opsz` barely helps — only pinning it does.** Restricting the axis to `16–48` still costs 90.3 KB against 40.9 KB pinned, because **the cost is *having* a second axis at all — a full extra set of `gvar` deltas for every glyph — not the width of its range.** Restricting weight alone buys only 29.6%. That single fact reframes the entire decision.

**A real Newsreader italic costs 40.9 KB** in latin at `wght 400–700`, or 24.6 KB subset to the glyphs actually used — not 143.6 KB. What costs roughly **50 KB per face and ~100 KB across both** is optical sizing. Pin `opsz` on both faces and Newsreader goes **272.4 KB → 78.1 KB**, taking the whole font payload **331.4 KB → 137.1 KB, a 58.6% cut**, while keeping a genuine italic *and* a 400–700 weight range. So the question on the table was never "is the italic worth it." It is **"is continuous optical sizing worth ~100 KB?"** — and `src/app/layout.tsx` documents `axes: ["opsz"]` as a deliberate decision with a devtools-verified effect, so that is exactly what gets forfeited. Forfeit it. Two pinned cuts — one text `opsz`, one display `opsz` — deliver a real optical distinction where it is visible, and the continuum between them is the part nobody can see.

Three things change the shape of that recommendation and must be priced with it.

**It is not a one-line diff.** `next/font/google`'s `axes` option takes axis *names* only; there is no way to pin an axis to a value. The win therefore requires moving Newsreader to **`next/font/local` with checked-in instanced files** — and that is the real cost. Thien owns font updates manually from then on, and **`pnpm verify` cannot catch a bad instance.** A wrong pin, a mangled `gvar` table, or a subsetter that pruned a glyph in use will typecheck, lint, pass contrast and build cleanly. **Only a visual check in both themes will find it.** Budget that check into the task rather than after it.

**The move unlocks a second-order benefit.** `next/font/google` exposes `adjustFontFallback` as a boolean; for `next/font/local` it accepts only `'Arial' | 'Times New Roman' | false` — but local fonts also accept arbitrary **`declarations`**, so the metric-matched fallback can be hand-written instead of merely accepted. Copy verbatim what `next/font` currently emits for `Newsreader Fallback` (`ascent-override: 69.68%; descent-override: 25.12%; line-gap-override: 0.0%; size-adjust: 105.48%`) and the migration is CLS-neutral by construction.

**Do not reach for synthesised italic.** Newsreader ships no `ital` axis — Google Fonts policy requires two variable files for italic — so a second file is unavoidable whatever you do. Faux italic works by skewing roman outlines, which is at its worst on a display serif whose italic is genuinely drawn rather than sloped. At 24.6–40.9 KB instanced, **keep the real italic**; it stopped being the expensive thing three rows up the table.

Four operational notes so this does not go wrong in the doing. **`pyftsubset` has no instancing flags at all** — instancing is a separate tool: `fonttools varLib.instancer INPUT.ttf AXIS=LOC ... -o OUT.ttf`, with positional `AXIS=LOC` arguments taking a number, the literal `drop`, or colon-separated values. **Order matters — instance first, then subset**, because instancing leaves behind glyphs and deltas that the subsetter then prunes; reversing the two leaves bytes on the table. **Do not configure Brotli or gzip over the wire for these files**: measured on this build, transport compression over WOFF2 ranges from −0.52% to +0.00%, because WOFF2 is already Brotli-compressed internally. **Further `unicode-range` splitting is not worth pursuing** once `subsets: ["latin"]` is set — `next/font` already ships exactly one slice per face. And **keep `display: "swap"`**: `optional` zeroes CLS at no measurable LCP cost, but it means cold visitors on slow networks may never see Newsreader at all, which is a steep price for a metric that is already fine.

One live inconsistency surfaced by the same pass, independent of this work. **Only 108 of the 224 codepoints in the latin slice are actually used by Thien's content (≈48%)** — which is what makes the 24.6 KB used-glyphs-only row possible — but **eight characters present in his source are not in the latin slice at all**: Σ, π, ạ, ệ, ∈, ⇔, ≈ and ≥. Those already render in a system fallback today, mid-sentence, inside Newsreader or Plex text. Check whether any appear in visible prose; **`ạ` and `ệ` would show up in Vietnamese place names**, which is precisely the content this redesign is built around.

Two further corrections fall out. The comment in `src/app/layout.tsx` saying Plex Sans "ships as static faces, so the weights actually used have to be listed" is **out of date**: Google now serves one variable file for weights 400/500/600, so the weight list costs nothing and trimming it saves nothing. And all five Latin files are preloaded from the root layout, so **every one of them is preloaded on `/resume` too** — with an unexplained duplication in those preload tags, filed under open items below.

Be clear-eyed about what the font win buys. Because the LCP element is a text paragraph and `font-display: swap` is already in the served CSS, fonts are off the LCP critical path entirely — web.dev is unambiguous that "if you set a `font-display` value of anything other than `auto` or `block`, then text will always be visible during load, and LCP won't be blocked on an additional network request" ([web.dev/articles/optimize-lcp](https://web.dev/articles/optimize-lcp)). And because **TBT carries 30% of the Lighthouse performance score** — the single heaviest weight, against LCP and CLS at 25% each ([Lighthouse performance scoring](https://developer.chrome.com/docs/lighthouse/performance/performance-scoring/)) — a 194 KB font cut will move the Lighthouse number very little. It buys bandwidth, a narrower CLS window, and the right to spend bytes elsewhere. **The Lighthouse 90+ target is a hydration problem, and the two biggest remaining transfers are the 98.5 KB gzipped (823 KB raw) HTML document and the 13.5 KB render-blocking stylesheet**, not the fonts.

## The ranked build order: eleven moves, priced

Everything here is ordered by value per unit of effort and per kilobyte. The first group is free or better than free; the second group costs real budget and should only be entered by cutting something.

**Group one — free, near-free, or negative cost.**

| # | Move | Cost | Buys | Risk |
|---|---|---|---|---|
| 1 | Move Newsreader to `next/font/local`, `opsz` pinned (two cuts), `wght` narrowed to 400–700 | ~1–2 h plus a manual visual check | **−194.3 KB** transfer (font payload 331.4 → 137.1 KB), keeping a real italic | forfeits continuous optical sizing; **`pnpm verify` cannot catch a bad instance** |
| 2 | `content-visibility: auto` + `contain-intrinsic-size` on below-fold `<Section>`s | ~1 line per section, 0 KB | web.dev's own demo: **232 ms → 30 ms rendering (~7×)** ([web.dev](https://web.dev/articles/content-visibility)) | scroll-restoration and smooth anchor links misbehave into skipped subtrees |
| 3 | Gate the globe's draw loop on `contentvisibilityautostatechange` | ~10 lines, 0 KB | MDN names canvas explicitly as the use case; Baseline since Sept 2024 ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Element/contentvisibilityautostatechange_event)) | none material |
| 4 | Defer the Companion chunk behind `next/dynamic` + an idle/interaction trigger | medium | **−25.8 KB** off initial JS — 41% of the app-code allowance, for a decorative element | `dynamic()` must live in a `'use client'` module or it does not split |
| 5 | Click-to-orient on the globe canvas | ~20 lines | satisfies **WCAG 2.5.7** (see below); reuses the drag handler's unprojection | none |
| 6 | Hand-write great-circle quaternion drag (the `versor` maths, not the package) | ~40 lines | eliminates gimbal weirdness on drag | see the dependency note below |
| 7 | Inline SVG `feTurbulence` grain as a data URI, one fixed full-viewport overlay at 2–4% | a few hundred bytes | paper/film surface, re-themes for free, no image request ([CSS-Tricks](https://css-tricks.com/grainy-gradients/), [ibelick](https://ibelick.com/blog/create-grainy-backgrounds-with-css)) | **never animate it** — `feTurbulence` is CPU work at paint time |
| 8 | Gradient-based sheen instead of `backdrop-filter` glass | 0 KB | avoids **+3.5 ms GPU-process and +4.7 ms Mali driver per frame** (see below) | none |
| 9 | Scroll-driven `view()` timelines behind `@supports`, over a `perspective: 1px` + `translateZ` parallax base | 0 KB JS | off-main-thread depth-on-entry | **invisible in Firefox stable** — decoration only, never information |
| 10 | Layered canvas: static graticule/ocean on its own canvas, repainted only on resize | ~30 lines | web.dev's canonical canvas optimisation ([web.dev](https://web.dev/articles/canvas-performance)) | none |
| 11 | Subset the instanced Newsreader faces to the glyphs actually used | ~30 min, after #1 | a further **−16.3 KB** on the italic face (40.9 → 24.6 KB) | breaks silently the moment content uses a pruned glyph — must re-run on content change |

**Group two — expensive; enter only by cutting something.** The BFS crawl-frontier artifact (below) wants 30–60 KB of graph data plus ~8 KB of code, which is 60–110% of the entire application allowance. A `preserve-3d` DOM scene costs zero JavaScript but was measured at **200–600 MB of GPU memory in Chrome** for one modest environment, against ~7 MB static plus 50–100 MB temporary in an engine that does not allocate a layer per element ([Ekioh](https://www.ekioh.com/devblog/3d-environments-in-css/)); a single promoted 400×300 element at 2× DPR is **1.92 MB of layer memory** ([MSPK](https://mspk.substack.com/p/what-will-change-actually-does-to)), so 100 elements is ~190 MB and a plausible tab crash on a low-end Android. Any WebGL micro-wrapper spends 15–38 KB to buy frame time that measurement says is not needed. And any scroll library is a budget renegotiation.

**One honest conflict to resolve.** `versor` 0.2.0 is **977 B gzipped** ([Bundlephobia](https://bundlephobia.com/api/size?package=versor)) and is the single cheapest meaningful upgrade in the entire catalogue — the d3 community's canonical answer to dragging a sphere without gimbal artefacts, at 1.6% of the application allowance. It is also a runtime dependency, and the Playground Earth plan says "No new runtime dependency. Not one." Both positions are right. The resolution is to keep the rule and write the ~40 lines of quaternion composition by hand, because the maths is published and the maintenance surface of forty lines you own is smaller than the maintenance surface of a package you do not. If that feels like false economy, take the package knowingly — but do not pretend the rule was never there.

**Also flag, do not quote: Bundlephobia returns `d3-geo` 3.1.1 as 37,059 B minified but 709 B gzipped.** A 52:1 ratio is not physically possible for JavaScript; that figure is a measurement artefact and must not enter any budget.

## Playground Earth survives the evidence, with six corrections

The committed direction is sound, and it is sound for reasons stronger than the ones it was chosen for. Three of them are worth naming because they are exactly the failure modes the genre is known for.

**It dodges scrolljacking by construction.** Nielsen Norman Group's usability testing found that "the majority of study participants were at least mildly disoriented by scrolljacking", that disorientation was "severely exacerbated when scrolljacks were excessively lengthy", that participants sometimes "interpreted the scrolljack as a bug", that **task-oriented users showed significantly lower tolerance than exploratory browsers**, and that "mobile experiences proved substantially worse than desktop" — with an explicit recommendation to exclude it from mobile and reserve it for below-the-fold content ([NN/g, *Scrolljacking 101*](https://www.nngroup.com/articles/scrolljacking-101/)). A below-the-fold globe you drag directly, whose bird advances exactly as fast as you turn the planet, takes over no input the visitor has already learned. It is *direct manipulation*, not scroll coupling — and NN/g's own remediation list reads like a description of where the globe already sits. This is the design's strongest structural advantage and it should be defended: **do not later couple the flight to scroll position.**

**Its static half is the answer to the interaction-rate problem.** Archie Tse's widely reported figure from a 2016 Malofiej talk is that readers interact with only about **10–15% of graphics** ([Fast Company](https://www.fastcompany.com/3069008/the-problem-with-interactive-graphics); [Dominikus Baur](https://medium.com/@dominikus/the-end-of-interactive-visualizations-52c585dcafcb) — both URLs refused direct fetch in this research, so the figure is reported from search-index summaries), and it is independently corroborated by the New York Times' finding, quoted in Distill, that "only a fraction of readers interact with non-static content" ([Distill, *Communicating with Interactive Articles*](https://distill.pub/2020/communicating-with-interactive-articles/)). That is not an argument against the globe. It is a *specification*: the server-rendered reading must carry the whole claim, and the interaction is the second layer that rewards the engineer who leans in. The plan's architecture — seven worlds, every plaque and every rail number server-rendered and complete before one byte of canvas code loads, with a test asserting completeness when the lazy chunk 404s — is that specification implemented. It is also, for free, the reduced-motion answer, the no-JS answer, and most of the WCAG answer.

**Its honesty rule is the actual differentiator.** Marlow & Dabbish's interview study of GitHub-based hiring found that profile cues were treated as more reliable than résumé information because behaviour traces are hard to fake, and critically that "employers only chose to look at those activity traces that are easy to verify quickly" ([CSCW '13](https://dl.acm.org/doi/10.1145/2441776.2441794) — 2013, so treat the mechanism as durable and the specifics as dated). Every durable engineer portfolio in the research fails the test "could this hook be swapped onto someone else's résumé?" — daedalOS cannot be lifted off Dustin Brett ([12,000+ GitHub stars](https://github.com/DustinBrett/daedalOS)), the annual CSS feat cannot be lifted off Lynn Fisher ([CSS-Tricks case study](https://css-tricks.com/case-study-lynnandtonic-com-2019-refresh/)), the simulations cannot be lifted off Bartosz Ciechanowski ([ciechanow.ski](https://ciechanow.ski/)). A globe alone *can* be lifted onto anyone. A globe whose every drawn object is either a verbatim quote of one authored field or a self-declared decoration, enforced string-for-string by a test, cannot. **That test is the moat, not the projection maths.**

Six corrections follow from the evidence.

**One: the drag alone fails WCAG 2.5.7, and the keyboard map does not save it.** This is the sharpest finding in the accessibility research and it is counterintuitive. The criterion reads "All functionality that uses a dragging movement for operation can be achieved by a **single pointer without dragging**", and it exists for people who *use* a pointer — head pointer, eye-gaze, mouth stick, trackball, speech-driven mouse emulator — but cannot hold and move one ([Understanding SC 2.5.7](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)). **Arrow-key rotation satisfies 2.1.1 and leaves 2.5.7 failing.** The good news is that the plan already contains the compliant alternative and does not know it: `GlobeControls.focusWorld(id)`, driven by clicking a world in the server-rendered list, is W3C's "named destinations" pattern, and "Take the flight" as a `<button>` is a single-pointer alternative to dragging east. Name them as the 2.5.7 answer, add **click-to-orient on the canvas itself** — the literal application of G219 Example 4, "a radial control widget allows changing values by clicking/tapping positions on the control" ([Technique G219](https://www.w3.org/WAI/WCAG22/Techniques/general/G219)) — and assert it in Playwright with `page.click()` only, never `mouse.down/move/up`. What does *not* satisfy it: a flick-to-spin affordance (also a 2.5.1 Level A failure) and a press-and-hold direction button.

**Two: forced colors is the hole under the whole Blueprint system.** `forced-colors: active` rewrites `color`, `background-color`, `border-color`, `outline-color` and SVG `fill`/`stroke` at paint time, forces `box-shadow` and `text-shadow` to `none`, and forces `background-image` to `none` except url-based images — **and it does not touch canvas bitmaps at all** ([MDN, `forced-colors`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/forced-colors)). For a canvas-drawn, hairline-ruled, single-hue design that is four distinct breakages at once: any rule drawn with `box-shadow` vanishes; any tonal ground drawn with a gradient vanishes; the blue accent collapses to `LinkText`/`CanvasText` so **annotation and body text become indistinguishable — a use-of-colour problem, not a cosmetic one**; and the globe keeps its authored day/night palette against a black-or-white page, possibly below 3:1 against `Canvas`. The mechanism the plan already uses to read semantic aliases at draw time via `getComputedStyle` is also the fix — redraw from system colours when `matchMedia("(forced-colors: active)")` matches — but the *non-chromatic* re-establishment of the annotation/accent distinction (an underline, a weight, a glyph) has to be designed, not bolted on. Note also that the browser picks system colours from **native element semantics, not ARIA roles**: `role="button"` on a `div` will not trigger `ButtonText`.

**Three: glass cannot sit next to the globe on mobile, and the reason is measured.** On a Samsung Galaxy A15 running Chrome 153, seven panels using `backdrop-filter: blur(18px) saturate(1.3)` dropped a 90 Hz app to **75–80% of target frames**, costing **≈3.5 ms of GPU-process time and ≈4.7 ms of Mali driver time per frame**; removing the blur by CSS alone restored 98.9% of frames and took p95 frame time from **22.3 ms to 11.2 ms** ([Station-Sciences/bot-crossing #74](https://github.com/Station-Sciences/bot-crossing/issues/74)). The mechanism is the part that matters here: Android Chrome re-renders every backdrop blur on **the same GPU-process thread that executes the canvas/WebGL command stream**, so a frosted panel over the globe does not cost 1.8 ms + 3.5 ms independently — it serialises. Cost scales with panel area, not blur radius, and past roughly 20px radius the cost rises faster than the visual difference ([CodeFronts](https://codefronts.com/motion/css-transition-designs/glassmorphism-hover-transition/)). An independent mobile-performance PR measured **60–80% faster** by replacing blur with gradient-based translucency at zero GPU blur cost ([itexpert120/journal-pwa #4](https://github.com/itexpert120/journal-pwa/pull/4)). Use gradients. If glass is non-negotiable somewhere, ship the one-line mitigation from that issue: `@media (max-width: 600px) { .panel { backdrop-filter: none; } }`.

**Four: "the lazy chunk does not touch the initial budget" is an assumption, not a measurement.** Turbopack merges chunks below `minChunkSize: 50000` uncompressed and up to `maxMergeChunkSize: 200000`, which is why this project's own removal of ~1,040 lines of client code moved only 4.5 KB. The globe's ~53 KB of coastline data plus its projector may or may not land where the plan expects. **Next 16 also removed the `size` and `First Load JS` metrics from `next build` output** as "inaccurate in server-driven architectures using React Server Components", so the framework will no longer tell you ([Next.js 16 upgrade guide, mirrored in `node_modules/next/dist/docs/01-app/02-guides/upgrading/version-16.md`; see also the [Next.js 16 blog](https://nextjs.org/blog/next-16)]). Verify the fence with `pnpm next experimental-analyze --output` and commit the diff artefact, because it is the only tool in Next 16 that answers *why* a chunk grew, with import chains.

**Five: the plan's budget baseline is one of two conflicting numbers.** The plan hard-codes 188.2 KB as measured. See the open-items section — do not gate on it until it is reconciled.

**Six: the Workshop needs a payload, not just a process.** Nine authored stations resolved from real fields is honest and satisfies the honesty rule, but a process walk is structurally closer to the patterns the restraint literature condemns — unfalsifiable self-description — than to the checkable artifact everything else in this research points toward. Give the Workshop a *run* worth watching: make the 17-hours-to-3-minutes rewrite the project the stations are executed against, with the predict-and-reveal artifact below as the payoff of the run. Then the process is evidenced by its output rather than asserted by its diagram.

## The counter-evidence is the brief: where creative, 3D and luxury each mean something narrower than they sound

**Creative.** The award evidence and the hiring evidence are measuring different outcomes, and conflating them is the trap. Bruno Simon's drivable-car WebGL portfolio won Awwwards Site of the Year and drew **400,000+ visitors** ([Awwwards](https://www.awwwards.com/bruno-simon-portfolio-wins-site-of-the-month-november.html)) — and what it converted into was **ThreeJS Journey, a training business**, not a hire ([case study](https://medium.com/@bruno_simon/bruno-simon-portfolio-case-study-960402cc259b)). The only direct survey of the question reached 300+ recruiters and React team leads, got 60+ responses, and found that hiring managers look at portfolio sites while rating their impact on hiring chances at the bottom of a 0–5 scale; respondents volunteered two specific downside risks — *"a bad design can make you look incompetent"* and *"Websites have to be maintained. Broken links in portfolios were only a few weeks old"* ([Profy.dev via DEV.to](https://dev.to/profydev/this-survey-among-60-hiring-managers-reveals-don-t-waste-your-time-on-a-react-portfolio-website-17ge); note the author sells a product whose pitch is that portfolios are the wrong investment). **No study compares hiring outcomes between creative and plain engineer portfolios. That experiment does not exist.** What the evidence does support is an architectural claim rather than a taste one: creativity placed *after* the scannable layer carries reach with no downside, and the `/resume` route — content-derived rather than hand-maintained — is already a stronger version of the dual-mode pattern than any example in the literature. Also worth knowing before over-indexing on awards: the chaptered-narrative portfolio that Awwwards nominated in September 2026 drew a jury spread of **5.0 to 10.0 with an average around 7.36** ([Awwwards, Four-Chapter Portfolio](https://www.awwwards.com/sites/four-chapter-portfolio)). The format divides juries; it does not universally impress. Its tags, incidentally, were CSS and JavaScript with no 3D tag at all.

**Interactive.** The 10–15% figure above is the governing constraint, and there is a second one beside it: Distill notes that the picture is contested, with other research finding readers do engage "when it is a core part of the article's message", and that some of the NYT's and Washington Post's most-read articles are interactive ([Distill](https://distill.pub/2020/communicating-with-interactive-articles/)). The synthesis is a testable rule — **an artifact must be fully persuasive with JavaScript disabled, and the interaction must be the mechanism the claim is about, not a wrapper around it.** Distill's five affordances give a usable gimmick test: connecting people and data, making systems playful, prompting self-reflection, personalising reading, reducing cognitive load. Ask which one an artifact uses and whether the same point could be made in a sentence. If the answer is "none" and "yes", it is decoration.

**3D.** The measured position is that a hand-written Canvas 2D pseudo-3D scene is the right tool and will remain so. The crossover to WebGL is a function of *draw calls per frame*, not of how three-dimensional something looks: Canvas 2D carries per-draw binding overhead of single-digit microseconds while WebGL carries a fixed setup cost and near-zero marginal cost per batched primitive, so hundreds of distinct filled or stroked shapes stay comfortably in Canvas 2D and many thousands of independently transformed primitives per frame is where batching begins to matter. **Nobody has published the actual crossover measurement** for an interactive pseudo-3D scene — the honest statement is that it is an inference from mechanism, and that at 1.8 ms/frame this project has close to an order of magnitude of headroom before Canvas 2D's overhead binds. The thing that would genuinely force WebGL is not object count but *per-pixel* work: real lighting, refraction, depth of field, volumetric atmosphere. Those are shader problems with no Canvas 2D equivalent at any object count — and none of them are in this design. The two practical extensions are painter's-algorithm depth sorting (one depth scalar per polygon, sort far-to-near, no depth buffer needed) and the layered-canvas pattern; the one primitive to avoid is `shadowBlur`, which web.dev singles out as "very expensive" ([web.dev](https://web.dev/articles/canvas-performance)). Pre-render soft shadows to a sprite once instead.

**Scroll-driven CSS is the best payoff-per-byte technique in the catalogue and cannot carry information.** `animation-timeline` runs off the main thread with zero JavaScript, but it is **not Baseline as of September 2026 because Firefox has not shipped it in stable** — web-platform-dx records Baseline as "blocked since September 2025 by Firefox", and MDN carries the banner "This feature is not Baseline because it does not work in some of the most widely-used browsers" ([Web Platform Features Explorer](https://web-platform-dx.github.io/web-features-explorer/features/scroll-driven-animations/); [MDN, `animation-timeline`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/animation-timeline)). Caniuse figures in this research disagree (**87.22%** versus **82.58%** from a secondary source), so report the range, not a number. Multiple 2026 blog posts assert universal support or "Firefox 132+ stable"; they are wrong, and they are content-farm domains. The design rule is absolute: **wrap it in `@supports`, and never let an `animation-timeline` carry a fact.** A progress rail, a chapter counter or a revealing label driven only by a scroll timeline is invisible to a meaningful share of visitors — the same failure this project's own "the rail carries facts already true in the content layer" rule exists to prevent. The acceptance test for every scroll-driven rule is that the un-animated state is the correct, complete state.

**Luxury.** The evidence base here is thin and asymmetric, and the one section with real convergent numbers is motion. Three independent systems agree closely enough to build a token set: Material 3's duration ladder puts dialogs and drawers at **300 ms** as the most common value with icon transitions at 150 ms and tooltips at 200 ms, and pairs decelerate easing with arrival and accelerate with departure ([M3 easing and duration tokens](https://m3.material.io/styles/motion/easing-and-duration/tokens-specs)); Vercel Labs puts micro-interactions at 100–150 ms, standard UI at 150–250 ms, modals at 200–300 ms, caps UI animation at **300 ms**, and runs **exits ~20% faster than entrances** ([vercel-labs/open-agents](https://github.com/vercel-labs/open-agents/blob/main/.agents/skills/web-animation-design/SKILL.md)); Emil Kowalski argues `ease-out` at 200 ms feels faster than `ease-in` at 200 ms because it front-loads the response, and that `ease-in` should never be used on UI ([emilkowal.ski, *Great animations*](https://emilkowal.ski/ui/great-animations)). A defensible token set for this project — labelled as synthesis, not quotation — is `--ease-out: cubic-bezier(0.215, 0.61, 0.355, 1)` as the single workhorse, `--ease-out-expo: cubic-bezier(0.19, 1, 0.22, 1)` reserved for the one or two singular moments, durations of 120 ms for hover, 200 ms for UI and 280 ms for panels, exits at 0.8×. The named anti-patterns are specific and easy to check: `linear` on interactive UI, animating from `scale(0)` rather than `scale(0.95)`, hover animation unguarded on touch, mismatched timing between a modal and its overlay, and **animating anything the visitor does repeatedly while reading**.

For everything else, the honest summary is that "luxury" resolves to three things this project can actually act on. **Restraint is the only well-evidenced signal**, and the one authoritative numeric source is Butterick — body text at 15–25px on the web, line spacing at **120–145%**, measure at **45–90 characters** ([Practical Typography](https://practicaltypography.com/typography-in-ten-minutes.html)). Hold the column at 60–68ch, near the middle of that band. **Refinement invisible until looked for is the actual mechanism**: Swisstopo's cartographers hid a marmot in Alpine contour lines and a fish in the grooves of a French nature preserve inside official maps, undetected for years ([AIGA Eye on Design](https://eyeondesign.aiga.org/for-decades-cartographers-have-been-hiding-covert-illustrations-inside-of-switzerlands-official-maps/)), and Eduard Imhof's reputation rests on continuous tonal relief applied to a line medium ([Esri ArcGIS Blog](https://www.esri.com/arcgis-blog/products/arcgis-pro/mapping/imhof-ish-cartography-now-everywhere-can-look-like-switzerland)). The generalisable rule is that **a technical artefact becomes luxurious at the point where its maker has clearly spent effort nobody asked for and few will notice** — correctly hung punctuation, tabular figures that keep rail columns from jittering, rules that align across sections, a focus ring drawn in the same hairline vocabulary as everything else. That is also the Imhof lesson for the tone axis: tone should behave like relief shading, modelling depth across a page-long surface, not decorating a component. **And restraint-as-luxury has a named commercial exemplar** in Aesop, whose ethos is described as "achieving the maximum effect with the minimal amount of materials" ([Design Anthology](https://design-anthology.com/story/aesop-by-design)).

Four cautions attach. **The blueprint aesthetic is now a documented 2026 trend**, described in exactly this project's own vocabulary — "clean, instructional styling with deconstructed illustrations, thin-line connectors, monospaced typography, and two-color palettes" ([Kittl](https://www.kittl.com/blogs/blueprint-graphic-design-trend-stl/)). Being on-trend is not being distinctive, and a trend's trailing edge is where distinctive becomes template. The differentiator a trend deck cannot copy is that **the rail's facts are computed from the content layer and are therefore true.** **Didone is both a cliché and a category error** — Editorial New and Didot are fashion-plate faces, not drawing-office faces, and they are "appearing everywhere". **The luxury literature actively recommends thin weight variants, and WCAG 2.2 AA forbids them**: `#999` on `#fff` is about 2.85:1 and fails; `#767676` is about 4.54:1 and is the practical lightest passing grey on pure white, which moves darker still on a tinted paper ground. The contrast gate wins that argument, and this project's existing rule to check tertiary tones against `--color-paper-deep` rather than `--color-paper` is correct. A gold accent is the same trap in a different colour: gold reads as luxury in the world because it is *specular*, and a screen can only render a flat mid-saturation yellow-brown, so any gold proposal will either fail contrast against `--color-paper-deep` or be darkened until it stops reading as gold. And **cyanotype is cyan-on-white — a light medium** — so the night theme is not historically grounded and has to earn itself as a distinct material (a drawing-office lamp, a lightbox, a negative print) rather than as an inverted day theme.

Two material decisions follow that are worth stating as direction. **Use a line-weight ladder, not an elevation ladder.** Technical drawings have no drop shadows; they have line weights. The transferable lesson from the shadow literature — that depth is several faint things rather than one strong thing ([Theo Soti](https://theosoti.com/blog/designing-shadows/)) — translates into 0.5px construction lines, 1px object rules, 1.5–2px for the single emphasised edge, with the shadow *technique* reserved for the one or two places something genuinely floats. And **keep grain behind text, never over it**: 2–4% is subliminal, 5–8% is visible, and overlaying noise on a text block means the measured contrast ratio of the token pair no longer describes what is on screen ([Ultimate Design Tools](https://ultimatedesigntools.com/blog/css-noise-textures-guide/)). One fixed, pointer-events-none, full-viewport overlay, generated once.

One last empirical anchor for the whole aesthetic argument, and its limit. Kurosu & Kashimura's 1995 Hitachi study tested 26 ATM interface variations with **252 participants** and found the correlation between rated aesthetic appeal and *perceived* ease of use stronger than between appeal and *actual* ease of use ([NN/g, *The Aesthetic-Usability Effect*](https://www.nngroup.com/articles/aesthetic-usability-effect/)). That is citable evidence that refinement buys measured tolerance — and NN/g's own framing bounds it: aesthetics buy forgiveness for *minor* problems. For a portfolio the reading is that polish raises the perceived competence of the engineering, which is precisely the claim the site is making. It is not a substitute for the site working.

## WCAG 2.2 settles three arguments this project has been having

**The 19px-versus-24px question is resolved, and the answer is that the project has been measuring the wrong criterion.** At AA, 2.4.11 Focus Not Obscured (Minimum) requires only that a focused component is "**not entirely hidden** due to author-created content" — partial obscuring passes, W3C states outright that a "partly obscured component can still be very visible", and **there is no pixel threshold anywhere in the criterion** ([Understanding SC 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)). A 19px sliver passes. Only 2.4.12 (Enhanced, AAA) demands zero obscuring, and this project does not target AAA. The 24 figure belongs to a different criterion: 2.5.8 Target Size (Minimum) requires 24×24 CSS pixels, with a spacing exception measured as a **24 CSS px diameter circle centred on each undersized target's bounding box** — so two undersized targets pass when their centres are ≥24 px apart, and **if both targets are already ≥24×24 the spacing exception is irrelevant and any gap, including zero, passes** ([Understanding SC 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)). A 19px clearance between a companion and a sticky control is conformant on both readings. The residual risks worth actually testing are reverse-tabbing under sticky chrome and `scroll-padding` covering only one edge — those produce *entirely* hidden components, which is the real 2.4.11 failure. Apply `scroll-padding-top` in `rem` to the **scroll container**, not the element, because Safari requires it there ([TetraLogical](https://tetralogical.com/blog/2023/06/08/focus-in-view/)).

**The motion obligation at AA is narrower than its reputation, and it binds in one specific place.** 2.3.3 Animation from Interactions is **Level AAA and not required at AA**, which means a scroll-driven journey animating only in response to the user's own scrolling is largely outside the AA motion surface ([Understanding SC 2.3.3](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)). What does bind is **2.2.2 Pause, Stop, Hide, which is Level A**, applies to moving content that "starts automatically, lasts more than five seconds, and is presented in parallel with other content", and is **not satisfied by honouring `prefers-reduced-motion`** — it wants an in-page mechanism ([Understanding SC 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)). The practical consequence for Playground Earth is narrow and good: because the globe is user-initiated and returns to rest, 2.2.2 does not bite — *provided the satellite decoration and any idle spin never animate unattended*. The plan's decision to exclude the satellite's orbit from "something is moving" is exactly right, and it is right for a reason worth writing in the code comment. If any looping decoration is ever added, it needs a real `<button>` with `aria-pressed` that halts all non-essential motion and persists the choice.

**The canvas should be declared decorative, and that is a content commitment rather than a CSS one.** The decision rule is a single question: is there any fact, state or action available only through the canvas? If no, `aria-hidden="true"` with nothing focusable inside it — which removes the globe from 1.4.11 Non-text Contrast, from 4.1.2, and from most of 2.5.8 at a stroke, because "graphics are exempt when the information is also available elsewhere" ([Understanding SC 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)). If yes, the HTML Standard's model is real focusable fallback content inside the `<canvas>` element, one control per interactive region, with `drawFocusIfNeeded()` for the ring; hit regions are dead and `addHitRegion()` was removed ([WHATWG HTML Standard](https://html.spec.whatwg.org/multipage/canvas.html#best-practices)). For this project the honest reading is decorative — every career fact lives in `portfolio.ts` and renders as text — and the honesty rule makes that literally true. Note that `aria-hidden="true"` and `role="img"` are mutually exclusive, not a combination, and that axe-core's `aria-hidden-focus` rule will fire if any focusable control is left inside.

**Expose the journey as headings, not landmarks.** WebAIM's Screen Reader User Survey #10 (December 2023–January 2024, **1,539 valid responses**) found that when finding information on a long page, **71.6% navigate by headings and only 3.7% reach for landmarks**, and that heading levels are useful to 88.8% ([WebAIM Survey #10](https://webaim.org/projects/screenreadersurvey10/)). So: one `<h1>`, one `<h2>` per world or chapter in DOM order matching the narrative, with position carried in the heading *text* ("Chapter 3 of 7 — …") rather than in geometry. Do not make each stage a named `<section>` landmark; at seven-plus stages that floods the landmark list for the minority who use it with no benefit to the majority who don't. Use `role="status"` for transitions the user causes that do not move focus — "Globe reset", "Motion paused" — which is what 4.1.3 Status Messages asks for.

**Automated testing will not cover most of this.** For WCAG 2.2, **axe-core has exactly one rule — `target-size` — it is off by default unless you request the `wcag22aa` tag, and Deque's public position is that it is likely to remain the only one** ([Deque](https://www.deque.com/blog/axe-core-4-5-first-wcag-2-2-support-and-more/); [axe-core 4.13 rule descriptions](https://raw.githubusercontent.com/dequelabs/axe-core/develop/doc/rule-descriptions.md)). Nothing automated exists for 2.5.7, 2.4.11, 2.4.13, 2.2.2 or 2.3.1. The good news is that all of them are mechanically checkable in Playwright without axe: expose the globe's orientation in the DOM (`data-globe-lat`/`data-globe-lon`) purely so it is assertable rather than asserting on canvas pixels; for 2.4.11, focus every focusable element forwards *and* backwards and assert the intersection with sticky chrome never covers it entirely; for 2.5.2, press down on a marker, move away, release, and assert no navigation. Run the existing 2 themes × 3 tones matrix a second time with `test.use({ reducedMotion: 'reduce' })` and `forcedColors: 'active'` — 24 runs at 1–2 s each, which is a loop, not a rewrite. And `target-size` returns "incomplete" results as well as violations, so inspect `results.incomplete`; an all-green violations array with twelve incompletes is a false sense of safety.

**Finally, reduced motion means substituting a meaningful static state, not freezing.** For the globe, render the orientation the current chapter implies — the *end* frame, not frame zero — keep click-to-orient working with the transition instantaneous, and never blank the canvas, because a missing globe is a loss of information. Author in the **opt-in** order: static by default, every keyframe wrapped in `@media (prefers-reduced-motion: no-preference)`, which also matches server-rendered-by-default. One prevalence anchor worth carrying, from a source that cites its own figures: up to 40% of the population experiences vertigo at least once, 4% of US adults report chronic balance problems and 1.1% report chronic dizziness ([A List Apart, *Accessibility for Vestibular Disorders*](https://alistapart.com/article/accessibility-for-vestibular/)). And the reason "zero animation frames at rest" is the most valuable property this codebase already has is measured: a page running a continuous rAF graph drained **4% of a phone's battery in 15 minutes against <1% idle** ([cytoscape.js #2657](https://github.com/cytoscape/cytoscape.js/issues/2657)). Every technique added must preserve that. Note too that **iOS Low Power Mode clamps rAF to ~30 fps**, so any motion must be tuned by elapsed time, not per frame, or it runs at half speed for those users.

## Four artifacts his real work can become, and two to cut

The strongest pattern available for Thien's specific numbers has published research behind it. **Predict-and-reveal** — the NYT "You Draw It" adaptation of belief elicitation — presents a partly-drawn chart and asks the reader to commit to a guess before the real data appears; prediction prompts encourage self-explanation and **improve recall** ([Cornell INFO 3312/5312](https://info3312.infosci.cornell.edu/notes/interactivity.html); [Distill](https://distill.pub/2020/communicating-with-interactive-articles/)). The reason it matters here is epistemic: a number in a résumé bullet asks for belief, while a prediction makes the reader *produce* a competing estimate and feel the gap. For "17 hours to 3 minutes" a reader will guess 2×, 5×, maybe 10×. **The answer is about 340×.** The reveal does the persuading and the author never has to sound boastful.

| # | Artifact | Pattern | Cost | Verdict |
|---|---|---|---|---|
| 1 | **"Guess how much faster."** The retailer catalog rewrite: a slider to guess the new runtime, then the reveal at 3 minutes and **340×**, then a two-lane compressed-clock race where the HTML lane is still crawling when the reader scrolls away. Second beat: the faster version is also the *more complete* one — coverage 654 → 1,529, failures 3.9% → 0 | predict-and-reveal | ~150–250 lines, **well under 5 KB gz**, no library | **Build first.** Cheapest, strongest fact, best pattern fit |
| 2 | **A Damerau-Levenshtein matcher you can type into.** A real anonymised legacy machine identifier from the 1M+ record Schaeffler migration; the reader types a mangled version or picks a transposition/substitution/abbreviation, and the DP matrix fills live against his actual threshold | explorable explanation | ~200 lines, **under 3 KB gz** | **Build second.** Best proof-per-byte on the list |
| 3 | **Break the pipeline.** The eight-stage SKU governance pipeline drawn as eight real stages; inject a fault — merchant changes their DOM, API rate-limits, SKU arrives with no price — and watch which deterministic gate catches it and what would have reached production without it. The **$2.8M** attaches to the last gate as what it protects, not as a headline | fault injection into a sandboxed model | ~300–400 lines, **~6–10 KB gz** | **Build third, if publishable.** Most representative of the actual job |
| 4 | **The crawl frontier, replayed.** A few hundred anonymised nodes of the seller↔product graph; the reader picks the priority function — rating, review volume, product count, or naive FIFO — and watches BFS expand with a live "useful records per request" counter | making systems playful | ~400–600 lines; **~8 KB gz code plus 30–60 KB of data** | **Build fourth, or not at all.** The payload alone is 48–96% of the application allowance |

Artifact 2 is the one that deserves the most attention, because it proves something a résumé structurally cannot. It demonstrates *why Damerau and not plain Levenshtein* — transposition is the characteristic human data-entry error, and plain Levenshtein charges 2 for it. An engineer reading that immediately knows the algorithm was chosen for a reason rather than reached for. **That judgement is invisible in a bullet and unmistakable here.** It also needs one piece of data he has not yet written down: what "99.9% reconciliation accuracy" was reconciled *against*, and measured how. An unexplained 99.9% is a weaker claim than an explained 99.5%.

Artifact 4 is where the budget bites hardest. Precompute the layout offline and ship coordinates — never a force-layout library running at runtime — and encode the graph as compact typed arrays rather than verbose JSON. If it grows past a few thousand nodes, **cut it back rather than adding a backend**, because a backend would break the static-site premise that makes everything else cheap.

**Cut two things.** The Wordification speech-QA loop and the LLM reviewer classification project should not become interactive artifacts. Both are real work, but neither has a mechanism that becomes legible through interaction — the 99.9% validated-audio claim is better served by one annotated artifact, a real transcript diff showing a regeneration trigger firing, than by a widget. Four strong artifacts beat six, and each extra one costs budget the first four need.

On the origin arc specifically, the evidence is unusually thin and unusually consistent in what it does say. **No writing was found on building a personal website around a migration spine — no case study, no critique, no craft essay** — so there is no template and no warning. The adjacent material is suggestive: relocated designers interviewed about the experience consistently foreground *specific, unglamorous particulars* — language acquisition, visa bureaucracy, contract navigation — rather than arcs of triumph ([The Brand Identity](https://the-brandidentity.com/insight/relocating-abroad-as-a-creative-three-designers-provide-insights-on-culture-community-and-care)). That is the observable difference between testimony and sentiment, and it maps exactly onto this project's existing rail rule: **a migration spine earns its place when each stop carries a dated, checkable particular, and becomes sentimental when it carries only an emotion.** The one transferable formal idea found is from Migration Trail, where the cartographic view is the *ground* the narration happens over rather than the subject. Applied here: geography is the chapter index, not the content. And the arc should mean something specific and measured — layer one is biography, layer two is where his code runs (nationwide store-data audits across 20+ live integrations, 40+ merchants, at whatever granularity is publishable), so the distance between where he started and where his software now operates is *measured* rather than gestured at. Under no circumstances should a recruiter have to pass through someone's origin story to reach their experience; the `/resume` route already guarantees they don't.

Finally, what to *not* put on the site, because the critique literature is unusually consistent and converges on one principle — **cut anything that is a claim the reader cannot verify.** Skill percentage bars are the most universally condemned pattern, on the grounds that "no one knows what it actually means" and "no one believes made-up percentages" ([Scrimba](https://scrimba.com/articles/web-developer-portfolio-mistakes/); [showproof.io](https://showproof.io/guides/what-to-include-in-developer-portfolio/)). Forty-logo tech walls, generic mission statements and empty testimonial headings fail the same test. **Staleness is the only failure mode with negative expected value** rather than merely zero — a missing section costs nothing, an abandoned one costs credibility, and a recruiter named it unprompted. For a single-page site with no CMS that argues for content that does not require upkeep to stay true: measured facts about completed work age well; a "currently reading" list does not. One weak but directionally consistent signal from a 2026 Hacker News thread is worth noting: maintainers now actively filter for "AI slop" characteristics in submitted personal sites, which raises the value of anything obviously expensive to fake. A hand-built artifact driven by real numbers from real work is close to unfakeable.

## What is not known, including the site's current JavaScript number

**The budget baseline is contested and must be reconciled before anything is gated on it.** The project's own tracker records **188.2 KB** of JavaScript for this branch, measured by `scripts/perf.mjs` via CDP `request.sizes().responseBodySize`. An independent curl-based measurement of the same build, fetching all 11 chunks requested by `/` with gzip, returns **228,394 B = 223.0 KB**. Three candidate explanations were offered and none was verified: the `.next` directory on disk may be from a later build than the tracker row; CDP `responseBodySize` may under-report when a response is served from the preload cache; or the perf script's `page.on("response")` handler silently drops chunks whose `sizes()` throws — the script's own comment says this "under-reports rather than crashing the run." **These are two measurements of the same thing by different methods, not a regression.** The fix is cheap and should be done first: make `scripts/perf.mjs` count and print skipped responses, so a run that swallowed chunks is visibly different from one that did not, and cross-check against curl. Until then, the arithmetic in this report holds either way — against 223.0 KB the app code is ~33 KB over a 190 KB budget, against 188.2 KB it is exactly at budget with ~60.6 KB of app code — but the *gate* must not be set on an unreconciled number. Note also that Next 16 removed `First Load JS` from build output, so a CI check that greps build stdout for it will silently pass forever.

**Three artifact proposals depend on clearances that do not exist yet.** Artifact 3 is current-employer internal architecture: the eight real stage names, the gate conditions and the failure taxonomy all need clearing, or a deliberately generalised version shipped with "stage names generalised" stated on the page — which is a credibility gain, not a loss. Artifact 1 should say "a national retailer's catalog" rather than name the retailer, which costs nothing. Artifact 4 depends on USC dataset restrictions; a structurally faithful anonymised sample with an explicit note ("shape preserved, identities removed") is honest and sufficient. **Resolve all three before they enter a build plan**, not after.

**Several measurements this report would have liked do not exist in the published literature.** There is no credible measurement of the Canvas 2D → WebGL crossover for an interactive pseudo-3D scene; no published byte count for a hand-written WebGL scene (every source asserts "kilobytes" without measuring); no numeric benchmark of SVG filter cost at a stated size and device; no controlled measurement of 2D canvas frame time at DPR 1 versus 2 versus 3; no measurement of stacked `box-shadow` cost versus `filter: drop-shadow()`; no per-frame profile of a CSS 3D scene; and no published frame-time comparison of scroll-driven animations against a JS scroll listener doing the same parallax. The per-`drawImage` overhead figures that set Canvas 2D's ceiling (≈3–9.5 µs/call) are **2014 numbers on 2014 engines** and should be treated as order-of-magnitude only.

**The evidence base for the strategic questions is thinner still.** No eye-tracking or analytics study of engineer portfolio sites exists. No study measures interaction rates on personal sites — all the interaction-rate data comes from news publishing, where the audience is the general public, and an engineer-portfolio audience is self-selected and technical and plausibly engages more, but **there is no data confirming that**. No study compares hiring outcomes between creative and plain portfolios. No study measures whether predict-and-reveal improves *credibility* judgements as opposed to recall — the recall evidence is solid, the persuasion claim is inference. And no critique exists distinguishing genuine from sentimental treatments of personal-origin narratives, which is a good question that appears to be unanswered in public writing.

**Several statistics circulating in this space are unverifiable or probably fabricated, and are deliberately absent from this report.** Every recruiter-timing figure in the literature (6, 15, 30, 55, 60 and 90 seconds) is untraceable to any methodologically described study. A claim attributing to "the Stack Overflow Developer Survey 2024" the finding that "73% of hiring managers consider a strong portfolio more important than a perfect resume" is almost certainly fabricated — that survey surveys developers, not hiring managers. Two further hiring-manager figures ("71% say portfolio quality directly influences their hiring decision", "80% say a portfolio helps them assess real-world problem-solving") appear only on lead-generation sites with no survey named. A "WebAIM vestibular survey" reporting that 40% of users with vestibular impairments have problems with scrolling and that over 50% named parallax as a trigger **does not exist** — WebAIM's published surveys are screen-reader, low-vision and motor-disability surveys. The "28% of users report motion sickness" figure has no primary source. None of these should be used, even hedged.

**Three smaller open items.** The served HTML carries **10 preload tags for 5 unique font files.** The tags themselves are correctly formed — `crossorigin=""` is present, so this is *not* the classic CORS double-fetch that makes a browser download each file twice — and browsers should dedupe by URL. But the duplication is unexplained, and nobody has traced whether it originates in `next/font` emitting per call site, in the layout rendering twice, or somewhere else. It is cheap to investigate and should not be assumed benign. Second, whether `experimental.inlineCss: true` interacts badly with Tailwind v4 under Turbopack's Lightning CSS pipeline is undocumented either way, so test it rather than assuming — the Next docs specifically name atomic CSS as the case where it helps most. And Vercel Hobby gives Speed Insights only as a Real Experience Score with 24-hour and 7-day ranges; **per-metric LCP/INP/CLS field data requires Pro**, so lab measurement (`pnpm perf`, Lighthouse CI at `numberOfRuns: 5` with median aggregation) is the only signal available. Set the byte budget as an `error` from day one — it is the only number with zero run-to-run noise — and start the timing assertions as warnings, given this project's documented **196 ms same-commit TBT swing** and **456 ms LCP spread**.

## Conclusion

The most useful reframe in this research is that **the fancy thing and the fast thing are not in tension here — they are competing for different budgets.** The globe costs frame time, and there is nearly an order of magnitude of it spare. The luxury costs typographic and material discipline, which is free.
